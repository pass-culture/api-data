## 🎯 1. General principle

A/B testing on this API relies on the native **multi-revision Cloud Run** mechanism:
two revisions of the same service run in parallel. The Cloud Run traffic splitter
distributes requests between them according to a configurable ratio (e.g. 50/50).

Each revision embeds the code of **its variant** and exposes a different value
for the `AB_TEST_VARIANT_LABEL` environment variable. This variable is what allows
each response and each log to be attributed to its A/B group, throughout the entire chain:
Redis cache → API response → BigQuery sink.

---

## ☁️ 2. Multi-revision Cloud Run infrastructure

### Branch naming convention — CI/CD prerequisite

> 🔴 **Blocking**: A/B test branches **must** follow the `ab-test*` pattern
> (e.g. `ab-test-71-graph-music`). The CI/CD pipeline rejects any production deployment
> from a branch that does not match this pattern.

### Deployment

```
Cloud Run Service: recommendation-api-v2
  ├── Revision A: apireco-prod-v2-a9932b2-44t  → AB_TEST_VARIANT_LABEL=main
  │     Traffic: 50%
  └── Revision B: apireco-prod-v2-c1f4d3e-52b  → AB_TEST_VARIANT_LABEL=ab71-graph-music
        Traffic: 50%
```

> 💡 The `cloud_revision_name` is automatically generated by Cloud Run at each deployment
> (format: `apireco-prod-v2-{commit_hash}-{suffix}`). It must not be confused with
> `AB_TEST_VARIANT_LABEL`, which is a stable label defined manually.

### Environment variables per revision

| Variable | Baseline revision | Variant revision |
|---|---|---|
| `AB_TEST_VARIANT_LABEL` | `main` | `<short-test-name>` (e.g. `ab71-graph-music`) |

> ⚠️ **Critical check**: a variant revision whose `AB_TEST_VARIANT_LABEL` is not
> explicitly configured will inherit the default value `main` and will be
> **silently merged** with the control group in BigQuery analyses.
> Always verify the value in production via the Cloud Run startup logs.

## 🏷️ 3. `ab_test_variant_label` — the common thread

### Relationship with `cloud_revision_name`

Cloud Run automatically assigns a `cloud_revision_name` to each deployment
(e.g. `apireco-prod-v2-c1f4d3e-52b`). This name is the primary identifier used in BigQuery
analyses to attribute each row of `past_offer_context` to its exact revision.

`AB_TEST_VARIANT_LABEL` is a **stable and human-readable** label that complements this mechanism:

| Scenario | cloud_revision_name | AB_TEST_VARIANT_LABEL |
|---|---|---|
| Initial baseline deployment | `apireco-prod-v2-a9932b2-44t` | `main` |
| Initial variant deployment | `apireco-prod-v2-c1f4d3e-52b` | `ab71-graph-music` |
| Baseline hotfix (without invalidating the test) | `apireco-prod-v2-f7a01bc-61r` | `main` ← **stable** |
| Variant hotfix (without invalidating the test) | `apireco-prod-v2-2e8d994-70s` | `ab71-graph-music` ← **stable** |

> **Why two identifiers?** If a fix or optimisation is deployed on a variant during the test,
> Cloud Run generates a new `cloud_revision_name`. Without `AB_TEST_VARIANT_LABEL`, BigQuery
> analyses would see two distinct revisions where there is logically only one.
> `AB_TEST_VARIANT_LABEL` allows multiple `cloud_revision_name` values to be grouped
> under the same logical version.

### Naming convention

| Revision | Value |
|---|---|
| Baseline | `main` |
| A/B variant | `<short-test-name>` (e.g. `ab71-graph-music`) |


### Automatic propagation

`AB_TEST_VARIANT_LABEL` (env var, default: `"main"`) is automatically propagated in:

### API response — `ab_test` field (`RecommendationMetadata`)

The `ab_test` field already exists in the backend data contract (returned as `"abTest"` in JSON,
previously always `null`). It is now populated with `settings.AB_TEST_VARIANT_LABEL`:

```json
{
  "params": {
    "recoOrigin": "similar_offer",
    "modelOrigin": "default",
    "callId": "abc-123",
    "uniqueCallId": "def-456",
    "abTest": "ab71-graph-music"
  }
}
```

> ⚠️ **Data contract**: do not add new fields to `RecommendationMetadata`
> without coordinating with the backend. `ab_test` is the intended channel for variant identification.

### Cloud Run logs (request level)

```json
{
  "message": "📥 Incoming similar_offers request.",
  "ab_test_variant_label": "ab71-graph-music",
  ...
}
```

### Startup log (verification at startup)

`AB_TEST_VARIANT_LABEL` is logged in `show_api_config()` at the startup of each revision:

```json
{
  "message": "🔧 API Configuration",
  "AB_TEST_VARIANT_LABEL": "ab71-graph-music",
  ...
}
```

> Verify this value in the Cloud Run logs as soon as a new revision is deployed.

### BigQuery sink (`past_offer_context`)

> 📌 **Architecture**: `past_offer_context` is a **DBT model** based on
> `run_googleapis_com_stderr`, the BigQuery table that contains everything captured
> by the GCP Log Sink from `tracking.py`.

`ab_test_variant_label` is present in `context_extra_data.ab_test_variant_label`
and directly in each `TrackingLogPayload` row. This allows:

```sql
-- Compare booking rates by variant
-- Note: ab_test_variant_label groups Cloud Run revisions of the same logical version.
-- For a fine-grained analysis by exact revision, use cloud_revision_name instead.
SELECT
  ab_test_variant_label,
  COUNT(DISTINCT offer_id) AS offers_shown,
  -- join with the bookings table
FROM `past_offer_context`
WHERE DATE(date) BETWEEN '2026-08-01' AND '2026-08-31'
GROUP BY ab_test_variant_label
```

## 📋 4. Mandatory convention: the HACK for AB testing block

> ⚠️ **Non-negotiable prerequisite**: any code that differs between the two variants
> **must** be wrapped by the following markers. Without this convention, the
> variant code is invisible to human review or an AI audit agent.

### Markers

```python
# --- HACK for AB testing ---
# ... variant-specific code ...
# --- End of HACK for AB testing ---
```

### Mandatory content of the comment block

The comment inside the block must explain:

1. **Business context**: what feature is being A/B tested, on which playlist, for which users.
2. **What the variant changes**: which parameters are modified, which model is substituted.
3. **Trigger condition**: the exact condition that activates the hack (intercepted inputs).
4. **Why these choices**: justification of the logic (e.g. why a particular enum is excluded).
5. **Duration / population**: what percentage of users, over which period (if known).

### Canonical example (ab_test_music_graph)

```python
# --- HACK for AB testing ---
# Context: On an offer page, two playlists are displayed:
#   - Playlist 1 "Dans la même catégorie": shows offers from the *same* search_group_name as the current offer.
#   - Playlist 2 "Ca peut aussi te plaire": shows offers from *all other* search_group_names
#     (excluding the current offer's search_group_name).
#
# This AB test targets Playlist 2 for music offers (search_group_name = MUSIQUE).
# When the frontend requests "Ca peut aussi te plaire" for a MUSIQUE offer, it sends all search_group_names
# *except* MUSIQUE (and NONE — see below). We intercept this specific request and swap:
#   - the search_group_names back to [MUSIQUE]
#   - the retrieval model to 'graph' (Knowledge Graph based on music metadata)
# This allows us to A/B test the graph-based recommendation strategy vs. the standard coreservation model
# on the "Ca peut aussi te plaire" playlist for music, for 50% of users over one month.
#
# Why exclude SearchGroupNameEnum.NONE?
# NONE is a special placeholder for offers that have not been assigned a proper search_group_name.
# It is not a real content category. When building Playlist 2 ("Ca peut aussi te plaire"), the frontend
# excludes the current offer's search_group_name to avoid showing offers from the same category.
# However, NONE is always excluded from this exclusion logic — because filtering *out* NONE would
# mistakenly remove uncategorised offers that are still valid recommendations.
# In short: NONE is never treated as a "real" category to match or exclude against.
SECOND_MUSIQUE_PLAYLIST_SEARCH_GROUPS = set(SearchGroupNameEnum) - {
    SearchGroupNameEnum.MUSIQUE,
    SearchGroupNameEnum.NONE,  # NONE is not a real category — always excluded from playlist filtering logic
}
if (
    search_group_names is not None
    and set(search_group_names) == SECOND_MUSIQUE_PLAYLIST_SEARCH_GROUPS
    and retrieval_model == SimilarOfferModelChoices.coreservation
):
    logger.debug(
        "⚠️ 🧪 [A/B TEST] AB test hack triggered: => replacing "
        "search_group_names with ['MUSIQUE'] "
        "and forcing retrieval_model to 'graph'.",
        extra={
            "call_id": call_id,
            "playlist": "Ca peut aussi te plaire",
            "original_search_group_names": [s.value for s in search_group_names],
            "original_retrieval_model": retrieval_model.value,
            "new_search_group_names": [SearchGroupNameEnum.MUSIQUE.value],
            "new_retrieval_model": SimilarOfferModelChoices.graph.value,
        },
    )
    search_group_names = [SearchGroupNameEnum.MUSIQUE]
    retrieval_model = SimilarOfferModelChoices.graph
# --- End of HACK for AB testing ---
```

### Rules

- **One block per test** per file. If the test touches multiple files, each
  file has its own block with a consistent comment.
- The **trigger log** (`logger.debug` or `logger.info`) with the prefix
  `[A/B TEST]` is mandatory inside the block to trace each activation of the variant.
- The markers are detectable via `grep "# --- HACK for AB testing ---"` — this is
  the identifier used by the AI audit skill.

## ⚡ 5. HTTP cache — automatic isolation

The HTTP response cache (`ENDPOINT_RESPONSE_CACHE_ENABLED`) is **automatically isolated**
per variant. The value of `settings.AB_TEST_VARIANT_LABEL` is injected into the cache
signature directly in `RedisAPI.fetch_cached_response` and `store_endpoint_response`:

```python
# In connectors/redis_api.py — centralised, cannot be forgotten
versioned_signature = {**request_signature_data, "_ab_test_variant_label": settings.AB_TEST_VARIANT_LABEL}
```

**No endpoint should manually add `ab_test_variant_label`** to its
`request_signature_data`. This is done once, in the right place.

### Guarantee

Two Cloud Run revisions with different `AB_TEST_VARIANT_LABEL` values **will never share**
an HTTP cache entry, even for strictly identical requests (same `user_id`,
same `offer_id`, same geolocation, same filters).

## ⚠️ 6. Offer resolution cache — contextual decision

The offer resolution cache (`OFFER_RESOLUTION_CACHE_ENABLED`) — key:
`offer_resolution:r{resolution}:{h3_cell}:{item_id}` — is **shared across all
variants by default**.

### Why it is not isolated by default

Offer resolution (transforming a Vertex item into a physical offer with a venue) is
a geographical operation that does not depend on the A/B variant in most tests.
Systematically isolating it would double (or more) the Redis memory usage, with no
measurable benefit.

### When to isolate manually

| Situation | Action |
|---|---|
| The A/B test changes **only** the retrieval model (which item is recommended) | ✅ Do not isolate — resolving the same item to the same venue is identical across variants |
| The A/B test modifies **the resolution logic** (e.g. venue sorting criterion, search radius) | 🔴 **Isolate** by adding `AB_TEST_VARIANT_LABEL` to `build_offer_resolution_cache_key` |
| The A/B test changes **category filters** that influence which items reach resolution | ✅ Do not isolate — the items that reach resolution differ, but resolving a given item remains identical |

### How to isolate if necessary

In `src/connectors/redis_api.py`, modify `build_offer_resolution_cache_key`:

```python
# Before (shared across variants)
return f"{RedisAPI._OFFER_RESOLUTION_NAMESPACE}:r{resolution}:{h3_cell}:{item_id}"

# After (isolated per variant — use only if the test modifies the resolution logic)
from config import settings
return f"{RedisAPI._OFFER_RESOLUTION_NAMESPACE}:{settings.AB_TEST_VARIANT_LABEL}:r{resolution}:{h3_cell}:{item_id}"
```

> **Document this choice in the `# --- HACK for AB testing ---` block** of the relevant
> pipeline, with an explicit explanation of why the resolution cache is (or is not)
> isolated for this test.

### Verify that both variants appear in BigQuery

As soon as the test is launched, run this query to confirm that both values
of `ab_test_variant_label` are present in the sink.

> ⚠️ **Use `run_googleapis_com_stderr`, not `past_offer_context`** for real-time checks.
> `past_offer_context` is a DBT model that only refreshes nightly — it is not suitable
> for immediate post-launch validation. `run_googleapis_com_stderr` is the raw GCP Log Sink
> table and is continuously populated.

```sql
SELECT
  JSON_EXTRACT_SCALAR(json_payload, '$.ab_test_variant_label') AS ab_test_variant_label,
  COUNT(*) AS row_count,
  MIN(timestamp) AS first_seen,
  MAX(timestamp) AS last_seen
FROM `<project>.<dataset>.run_googleapis_com_stderr`
WHERE DATE(timestamp) >= '<test_start_date>'
GROUP BY ab_test_variant_label
ORDER BY row_count DESC
```

If only one variant appears, `AB_TEST_VARIANT_LABEL` is not correctly configured
on one of the Cloud Run revisions.

### Standard A/B analysis query

```sql
WITH base AS (
  SELECT
    JSON_EXTRACT_SCALAR(context_extra_data, '$.ab_test_variant_label') AS ab_test_variant_label,
    offer_id,
    user_id,
    call_id,
    offer_order,
    date
  FROM `<project>.<dataset>.past_offer_context`
  WHERE DATE(date) BETWEEN '<start>' AND '<end>'
    AND JSON_EXTRACT_SCALAR(context_extra_data, '$.context') = 'similar_offer'
)
SELECT
  ab_test_variant_label,
  COUNT(DISTINCT call_id) AS nb_playlists,
  COUNT(DISTINCT user_id) AS nb_users,
  COUNT(*) AS nb_offers_shown
FROM base
GROUP BY ab_test_variant_label
```

## ✅ 8. Pre-launch checklist

### Shared code base — fundamental rule

> The variant branch **must** be built **on top of** the baseline branch.
> No commit present in version A should be absent from version B.

This rule ensures that any difference observed in the results is solely
due to the code added in the `# --- HACK for AB testing ---` block, and not to an
accidental divergence between branches (missed merge, incorrect rebase, partial cherry-pick).

> ⚠️ This is not a strictly blocking rule, but any code base divergence
> must be **flagged as a critical WARNING** in the audit and explicitly justified
> before launch.

Verification:

```bash
# List commits present in main but absent from the variant branch
git --no-pager log origin/main ^origin/ab-test-<name> --oneline
# => If this list is not empty, baseline commits are missing from the variant.
```

### Watch out for logic differences outside the HACK block

Beyond the code explicitly wrapped in `# --- HACK for AB testing ---`, other
behavioural differences may exist between the two versions if the variant branch
diverges from the baseline without being tagged.

**Example of a difference found during the `ab_test_music_graph` A/B test**:

```python
# Baseline version (main) — Fallback Phase limited to the coreservation model
is_coreservation_model = retrieval_model == SimilarOfferModelChoices.coreservation
if is_coreservation_model and len(final_similar_offers) == 0:
    # fallback to playlist_recommendation...

# Variant version (A/B branch) — Fallback extended to ALL models
# The fallback applies to ALL retrieval models (including 'graph').
# Without this, the two A/B test groups would behave asymmetrically on zero-result cases:
# the control group (coreservation) would receive a fallback playlist while the test group (graph)
# would receive an empty response — penalising the test group independently of model quality.
if len(final_similar_offers) == 0:
    # fallback to playlist_recommendation...
```

This difference is not inside a `# --- HACK for AB testing ---` block but it
directly impacts the comparability of the groups. The AI audit skill must look for
this type of divergence by reading the full diff, not only the tagged blocks.

### Code

- [ ] A PR from the `ab-test-*` branch is created and labelled **`A/B Test`** to make the variant code visible and reviewable by the team before production launch
- [ ] The variant code is entirely wrapped by `# --- HACK for AB testing ---` / `# --- End of HACK for AB testing ---`
- [ ] The block comment describes: business context, changes, trigger conditions, justifications, edge cases
- [ ] A `logger.debug/info` with the prefix `[A/B TEST]` is present in the block and logs the before/after parameters
- [ ] `AB_TEST_VARIANT_LABEL` is **not** manually added to the `request_signature_data` of endpoints (this is automatic)
- [ ] The resolution cache decision is documented in the block (isolated or not, and why)
- [ ] The variant branch has **no missing commits** compared to the baseline

### Cloud Run deployment

- [ ] The **baseline** revision has `AB_TEST_VARIANT_LABEL=main`
- [ ] The **variant** revision has `AB_TEST_VARIANT_LABEL=<short-test-name>` (e.g. `ab71-graph-music`, no spaces)
- [ ] Both revisions have the correct traffic ratio configured in the traffic splitter
- [ ] Check the startup logs of each revision: `AB_TEST_VARIANT_LABEL` must appear in the logged config

### Post-launch validation (D+1)

- [ ] Both `ab_test_variant_label` values appear in BigQuery (query in section 7)
- [ ] Cloud Run logs show the `[A/B TEST]` trigger on the variant revision
- [ ] The HTTP cache shows no abnormal `cache HIT` on the variant side in the first few minutes
  (the first requests should all be MISSes, then HITs should come from the same variant)
- [ ] Request volumes are balanced between the two revisions
